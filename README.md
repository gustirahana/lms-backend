# JakIja React LMS — Backend

NestJS API for the JakIja-inspired learning management system. The API uses Supabase Auth for credentials and a server-managed session cookie for browser requests.

This repository contains the backend only; the frontend is maintained separately. It is a new React and NestJS implementation inspired by the feature areas in [JakIja](https://github.com/johansantri/jakija), not the upstream repository. This project is for learning and educational purposes.

## Local setup

### Requirements

- Node.js 20 or newer
- npm
- A Supabase project

### Start the API

Install dependencies and create the local environment file:

```sh
npm ci
cp .env.example .env
```

1. `SUPABASE_URL` is prefilled for the connected `lms-backend` project (`upqfqbxvxygmkhqmxpaw`). Set `SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY` using the project's API settings. Keep the secret key in the ignored `.env` or a deployment secret manager. Supabase is phasing out the legacy anon/service-role key names by the end of 2026; the older `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` variables remain supported as fallbacks for existing projects during migration.
2. Set `AUTH_ENCRYPTION_KEYS` to a key generated by `openssl rand -base64 32`, prefixed with its version, for example `v1:<generated-key>`.
3. Authenticate and link the Supabase CLI to the project, then apply the versioned migrations:

```sh
npx supabase login
npx supabase link --project-ref upqfqbxvxygmkhqmxpaw
npx supabase db push
```

The connected project currently has the baseline LMS schema and both follow-up index migrations applied. The migration filenames in this checkout match the hosted migration versions.
4. Start the development API:

```sh
npm run start:dev
```

The API listens on `http://localhost:4000/api` by default. Set `HOST=127.0.0.1` for a local-only listener; container deployments commonly use `HOST=0.0.0.0` behind their ingress or reverse proxy. Liveness is `/api/health`; readiness is `/api/health/ready`. The API exits in production when Supabase configuration or schema version 1 is missing.

The API sends Supabase publishable/secret keys only in the `apikey` header. It does not use a project API key as a bearer token. Authenticated `/user` and `/logout` calls send the user's Supabase access token as `Authorization: Bearer ...`.

This verifies the local gateway and HTTP wiring with a mocked `AuthService`. ## Local Supabase integration smoke

Start the local Supabase stack with email/password Auth enabled, then run `npm run test:supabase`. The smoke reads local status values from the pinned Supabase CLI without printing keys and refuses any API URL outside loopback. It creates and deletes synthetic users, then exercises backend login, session restore, refresh, logout, profile-trigger role protection, public-client denial for `app_sessions`, and cleanup retention. The test does not link to or contact a hosted project. In this environment, Docker published the local Supabase ports on all host interfaces (`0.0.0.0` and IPv6 wildcard), even with the project network's loopback binding option. Treat the local stack as reachable from your network: run it only on a trusted network, stop it after local checks, and do not use it as a production service. ## Browser authentication

- `POST /api/auth/login` accepts `{ "email": "...", "password": "..." }` and returns `{ "user": { "id": "...", "email": "..." } }`.
- `GET /api/auth/session` returns the current user.
- `POST /api/auth/refresh` rotates Supabase tokens and returns the current user.
- `POST /api/auth/logout` revokes the app session and clears the cookie.

The browser receives only a random 256-bit opaque cookie (`lms_session` locally, `__Host-lms_session` in production). The database stores its SHA-256 hash, never the raw cookie. Supabase access and refresh tokens are AES-256-GCM encrypted in `app_sessions`; encrypted values include a key version. The frontend must send `credentials: 'include'` and an allowed `Origin` for POST requests. Production cookies always use `Secure` and `HttpOnly`.

`VITE_APP_NAME`, `VITE_APP_VERSION`, and `VITE_APP_DEVICE` are public build metadata. CORS permits `X-App-Name`, `X-App-Version`, and `X-App-Device` headers, but the backend currently ignores them. They are not hashed into bearer credentials and never grant access. Vite values ship to browsers and cannot be secrets. Authentication comes from the server-issued session cookie and Supabase-validated user identity.

`AUTH_ENCRYPTION_KEYS` is a comma-separated key ring in `version:base64` form. To rotate keys, add a new key while retaining the old key, set `AUTH_ENCRYPTION_KEY_VERSION` to the new version, deploy, then re-encrypt existing rows or wait for their sessions to expire before removing the old key. Never reuse an encryption key for another purpose or commit keys.

## Supabase data and provisioning

The migration enables RLS on every application table, explicitly revokes table access from `public`, `anon`, and `authenticated`, and grants the server-only `service_role` access; it creates no client table policies. It also explicitly revokes default function execution and grants only the necessary RPCs to `service_role`. Keep these explicit grants and revokes in future migrations: new Supabase projects are changing default grants for public tables. The backend uses the Supabase secret key (or the legacy service-role key fallback) only on the server. Never expose that key or `AUTH_ENCRYPTION_KEYS` to the frontend.

### Hosted verification snapshot (2026-10-08)

The hosted `lms-backend` Supabase project was `ACTIVE_HEALTHY` with three migration versions recorded and API schema version 1. A read-only database check confirmed RLS on all 10 application tables, no `SELECT` for `anon` or `authenticated` on those tables, and server-role access. The five application functions deny execution to `anon` and `authenticated`; the service role has execution access. The Security Advisor reports 10 informational `rls_enabled_no_policy` notices, expected for the server-only table-access model with client privileges revoked.

The compiled API was started in production mode on loopback with the ignored backend `.env` and a temporary HTTPS origin. `/api/health/ready` returned 200 against the hosted schema; public `GET /api/courses` returned 200, and `GET /api/dashboard` returned 401 without a session. Both Socket.IO namespaces rejected connections without a session cookie. A temporary three-user hosted E2E then verified production `__Host-` cookie attributes, login, refresh and restore, the learner dashboard enrollment, notification isolation and ownership, learner/instructor course access, outsider denial, persisted classroom delivery only to authorized members, and namespace disconnection on logout. The frontend browser sign-in restored the hosted learner dashboard after reload. The temporary users and course were removed by exact IDs and confirmed absent. The browser’s local development origin did not establish Socket.IO; the verified production API checks used a temporary origin, not a deployed frontend domain.

Hosted Auth rejection checks returned 401 for session restore and refresh without a cookie. One login attempt for an unregistered synthetic address returned a generic 401 and did not set a session cookie; this did not create or modify a user.

This snapshot does not verify the eventual deployed frontend origin, production browser cookie behavior on that domain, multi-replica operation, or the chosen production network topology. Configure the exact frontend origin and cookie policy, then repeat browser HTTP and Socket.IO checks on the deployed domain before launch.

An Auth user insert trigger creates a learner profile. It ignores any role in user metadata. Promote instructors/admins and assign courses using privileged Supabase SQL or a future audited admin API. For example, after creating an Auth user, an operator can update `profiles.role`, create a `courses` row, and insert matching `course_instructors` or `course_enrollments` rows in the Supabase SQL editor. Course room access is checked against owner, instructor assignment, or active/completed enrollment on every join and message send.

To exercise a room with real accounts, replace the UUID placeholders in the Supabase SQL editor:

```sql
update public.profiles set role = 'instructor' where id = '<INSTRUCTOR_AUTH_USER_UUID>'::uuid;

insert into public.courses (owner_id, title, description, category, level, status)
values ('<INSTRUCTOR_AUTH_USER_UUID>'::uuid, 'LMS Room Demo', 'Private room demo', 'Demo', 'beginner', 'published')
returning id;

insert into public.course_enrollments (course_id, user_id, status)
values ('<RETURNED_COURSE_UUID>'::uuid, '<LEARNER_AUTH_USER_UUID>'::uuid, 'active');
```

The assigned instructor and active learner can then join that course room. The database has no public client write policies; these provisioning statements require a privileged operator.

`GET /api/courses` returns published courses only. `GET /api/dashboard` requires a valid session and returns `{ learner: { id, displayName, role }, stats: { hoursLearned, coursesInProgress, certificates }, courses: Course[] }`. Dashboard courses are the signed-in learner's active enrollments; metrics come from progress and certificate rows and are zero when those rows are absent.

## Realtime contract

Both Socket.IO namespaces require the same cookie session and exact allowed `Origin` as HTTP. The browser connects with credentials enabled.

### `/notifications`

- On connection, the server joins only `user:<authenticated-user-id>`.
- Client `notification:subscribe` takes `{}` and acknowledges `{ subscribed: true, notifications }` with up to 50 unread records; it cannot choose a room.
- Client `notification:read` takes `{ notificationId }`; the server updates only a row owned by the authenticated user and acknowledges `{ ok, id, readAt }` or `{ ok: false, error }`.
- Server emits `notification:new` and `notification:read` only to that user's sockets whose app sessions remain active. New notifications are persisted before delivery.

### `/classroom`

- `course:join` takes `{ courseId }`; only an owner, assigned instructor, or active/completed enrollee can join `course:<courseId>`.
- `course:leave` takes `{ courseId }`.
- `classroom:history:request` takes `{ courseId }` and returns the latest 50 persisted messages in chronological order after rechecking membership.
- `classroom:message:send` takes `{ courseId, body }`, with a 1–4000 character body. Sender identity comes from the session. The server rechecks room membership and database ACL, persists the message, then revalidates each recipient's session and course membership before emitting `classroom:message:new` to that socket.
- The server limits each user's classroom message sends to 30 per minute per API process.

No client-provided user ID or room name is trusted. Realtime rooms are scoped by namespace and membership; namespaces alone are not an authorization boundary.

## Production deployment

Set `NODE_ENV=production`, at least one exact HTTPS `FRONTEND_ORIGINS` entry, HTTPS `SUPABASE_URL`, the Supabase publishable and secret keys, `AUTH_ENCRYPTION_KEYS`, and `AUTH_ENCRYPTION_KEY_VERSION`. Set `TRUST_PROXY_HOPS` to the actual trusted proxy count. Serve the frontend and API on the same site or use a same-origin reverse proxy when possible, with `COOKIE_SAME_SITE=lax`. If they are genuinely cross-site, configure `COOKIE_SAME_SITE=none`; browser third-party-cookie policies may still block the session cookie, so verify the target browsers and deployment topology before launch. Production uses an in-memory per-process rate limiter; deploy a shared API gateway rate limit before running multiple API replicas. The current Socket.IO adapter is also process-local, so run one API replica until a shared Socket.IO adapter is configured.

In production, the API runs a privileged app-session cleanup once at startup and every 24 hours. It deletes expired sessions and revoked sessions older than 30 days; recently revoked rows remain for the retention window. The operation is idempotent, so multiple API replicas can run it safely. A warning is logged if a run fails, without session or token values. Do not expose cleanup as a learner endpoint. The project also has no billing, password recovery, signup policy, audited admin API, or database backup/restore automation yet. Review those operational requirements before serving real learners.

Refresh rotation keeps the previously stored encrypted token pair until Supabase's replacement pair is durably written. If the process or database write fails after Supabase accepts the old refresh token, the next request can retry with the stored parent token; Supabase Auth returns the active child token. The same opaque browser cookie remains valid, and a stranded database lock expires after 15 seconds. The local Supabase integration smoke exercises this recovery after both the lock lease and the configured 10-second reuse interval. This relies on Supabase Auth's parent-token recovery behavior; if the provider changes that contract or revokes the token family, the learner must sign in again. See [Supabase session refresh-token reuse behavior](https://supabase.com/docs/guides/auth/sessions).
